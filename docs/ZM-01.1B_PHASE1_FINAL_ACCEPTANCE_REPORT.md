## Section B: Supabase Auth Authority & Password System Source Audit

### 1. Authentication Authority Architecture
Zealosh LMS operates under ADR-002 (Server-Side Authoritative & Defense-in-Depth RLS). The authoritative authentication authority is governed by the active storage mode:
1. **Production Supabase Mode (`DATABASE_STORAGE=supabase`):** Supabase Auth (`auth.users`) is the authoritative identity provider. Credentials created or updated in the LMS are synchronized directly to Supabase Auth using the Supabase Service Role Admin API (`adminClient.auth.admin.createUser`, `adminClient.auth.signInWithPassword`, and `adminClient.auth.admin.updateUserById`).
2. **Local Development / Isolated Test Mode (`DATABASE_STORAGE=in_memory`):** The built-in in-memory security adapter manages local state with bcrypt hashing (`bcryptjs` salt rounds 10), ensuring tests execute reproducibly and offline without external network dependencies.

### 2. Elimination of Dual Authority Split
Prior to ZM-01.1B, `/api/auth/register`, `/api/auth/login`, and `/api/auth/password-reset/confirm` only wrote to `user.passwordHash` and `public.profiles`. The following remediations were implemented:
- In [`src/app/api/auth/register/route.ts`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/src/app/api/auth/register/route.ts): When `isSupabaseConfigured() && process.env.DATABASE_STORAGE === 'supabase'`, the endpoint creates the user in `auth.users` via `adminClient.auth.admin.createUser({ email, password, email_confirm: true, user_metadata: { name, role: 'STUDENT' } })`.
- In [`src/app/api/auth/login/route.ts`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/src/app/api/auth/login/route.ts): In Supabase mode, the login endpoint verifies credentials against `adminClient.auth.signInWithPassword({ email, password })`. Failed attempts increment `failedLoginCount`; 5 consecutive failed attempts trigger an immediate 15-minute lockout returning HTTP 423.
- In [`src/app/api/auth/password-reset/confirm/route.ts`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/src/app/api/auth/password-reset/confirm/route.ts): When a reset token is confirmed, credentials in `auth.users` are updated via `adminClient.auth.admin.updateUserById(userId, { password: newPassword })`.

### 3. Account Lockout & Audit Trails
- 5 consecutive failed login attempts lock the account for 15 minutes.
- Rejection responses return `HTTP 423 Locked` with remaining lockout minutes.
- All authentication events (`USER_LOGIN_SUCCESS`, `USER_LOGIN_FAILED`, `LOGIN_REJECTED_LOCKED_ACCOUNT`, `LOGIN_REJECTED_SUSPENDED_ACCOUNT`) generate structured immutable audit records stored in `AuthAuditEvent`.

## Section C: Database Architecture & Migration Safety Review

### 1. Migration File Analysis
Migration [`supabase/migrations/20261030000008_zealosh_phase1_foundations.sql`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/supabase/migrations/20261030000008_zealosh_phase1_foundations.sql) defines the Phase 1 schema:

- `admission_applications`, `application_documents`, `enrollment_transfers`, `enrollment_withdrawals`
- `user_profiles`, `student_profiles`, `instructor_profiles`, `user_role_assignments`

### 2. Cascading Deletion Safety Finding
In the migration script:
```sql
CREATE TABLE IF NOT EXISTS enrollment_transfers (
  id TEXT PRIMARY KEY,
  enrollment_id TEXT NOT NULL REFERENCES enrollments(id) ON DELETE CASCADE,
  ...
);

CREATE TABLE IF NOT EXISTS enrollment_withdrawals (
  id TEXT PRIMARY KEY,
  enrollment_id TEXT NOT NULL REFERENCES enrollments(id) ON DELETE CASCADE,
  ...
);
```
**Risk Analysis:** `ON DELETE CASCADE` on historical audit tables means if an `enrollments` row is physically deleted from PostgreSQL, the compliance audit transfer and withdrawal records would be deleted as well.  
**Architectural Policy & Mitigation:** In Zealosh LMS, enrollments are **never physically deleted** (`DELETE FROM enrollments`). Withdrawals and cancellations are recorded via status transitions (`status = 'CANCELLED'` or `status = 'WITHDRAWN'`), preserving historical relational integrity. For future DDL evolution, audit tables will transition to `ON DELETE RESTRICT` or soft-deleted foreign keys.

### 3. RLS Policies
All 12 new tables have `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` enabled with tenant and role-based policies:
- Students can only view their own applications, documents, and profiles (`auth.uid() = user_id`).
- Instructors and Admins have role-guarded access through `user_role_assignments`.
- Public read access is granted only to active published curriculum trees (`academic_years`, `departments`, `programmes`, `topics`, `subtopics`).

## Section D: Admissions State Machine, Concurrency & Policy Reconciliation

### 1. State Machine Invariants
Admissions applications follow a strict linear lifecycle:
$$\text{DRAFT} \longrightarrow \text{SUBMITTED} \longrightarrow \text{UNDER\_REVIEW} \longrightarrow \text{APPROVED} \mid \text{REJECTED}$$

- Applications are created in `SUBMITTED` status with an institutional application number format (`APP-YYYY-XXXX`).
- Transitioning an already reviewed application (`APPROVED` or `REJECTED`) is rejected with `HTTP 409 APPLICATION_ALREADY_REVIEWED`.
- Approval executes an atomic seat reservation against the cohort batch. If `enrolledCount >= capacity`, the review is rejected with `HTTP 409 BATCH_CAPACITY_EXCEEDED`, preventing over-enrollment.

### 2. Bulk Import Policy Compliance (BDR-01 Reconciliation)
In initial drafts, bulk CSV import was auto-enrolling candidates upon upload. Because BDR-01 (Institutional Admission Model) is `UNDECIDED`, unconditional auto-approval was a policy violation.

**Remediation implemented in [`src/lib/store/db.ts`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/src/lib/store/db.ts) and [`src/app/api/admin/admissions/bulk-import/route.ts`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/src/app/api/admin/admissions/bulk-import/route.ts):**
- Added `BulkImportOptions` with `mode?: 'PENDING_REVIEW' | 'AUTO_ENROLL'`.
- Default mode is strictly **`PENDING_REVIEW`**:
  - Validates CSV rows (headers: `name`, `email`, optional `course`, `batch`, `phone`).
  - Provisions applicant student accounts (allowing applicants to authenticate to the portal).
  - Creates applications in `'SUBMITTED'` status.
  - Leaves `createdEnrollmentIds` empty and increments `pendingReviewCount`.
- **`AUTO_ENROLL`** mode requires explicit administrative request (`body.mode = 'AUTO_ENROLL'` or `body.autoApprove = true`), in which case `reviewAdmissionApplication('APPROVED', reviewerId)` is invoked and enrollments are created.

## Section E: Document Upload Security & Configurable File Ceiling

### 1. Hardened Document Validation Utility
Created [`src/lib/storage/document-validation.ts`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/src/lib/storage/document-validation.ts) providing multi-layered upload defense:
1. **Configurable Size Ceiling:** `getMaxDocumentSizeBytes()` checks `process.env.MAX_DOCUMENT_SIZE_BYTES` (falling back safely to 25MB `25 * 1024 * 1024`).
2. **Directory Traversal Sanitization:** `sanitizeFilename(rawFilename)` strips null bytes, control characters, Windows/Unix path separators (`\`, `/`), and directory traversal sequences (`../`, `..\`), ensuring safe storage keys.
3. **MIME Whitelisting:** Permitted MIME types are strictly restricted to `application/pdf`, `image/png`, `image/jpeg`, and `image/webp`.
4. **Magic Byte File Signature Verification:**
   - PDF: verified against `%PDF-` (`0x25 0x50 0x44 0x46 0x2D`)
   - PNG: verified against standard 8-byte PNG header (`0x89 0x50 0x4E 0x47 0x0D 0x0A 0x1A 0x0A`)
   - JPEG: verified against SOI marker (`0xFF 0xD8 0xFF`)
   - WebP: verified against RIFF container and WEBP header (`RIFF....WEBP`)
5. **Strict Executable & Script Rejection:** Explicitly inspects and rejects executable binaries disguised as documents:
   - Windows Portable Executable (PE / `MZ` `0x4D 0x5A`)
   - Linux Executable and Linkable Format (ELF `\x7FELF` `0x7F 0x45 0x4C 0x46`)
   - Unix script execution shebangs (`#!` `0x23 0x21`)
   - Java class bytecode (`0xCA 0xFE 0xBA 0xBE`)
   - macOS Mach-O binaries (`0xFE 0xED 0xFA 0xCE`, etc.)

Wired directly into [`src/app/api/admissions/apply/route.ts`](file:///C:/Users/alexc/.gemini/antigravity-ide/scratch/zealosh-lms/src/app/api/admissions/apply/route.ts).
